# ChatCockpit 0.2.0-alpha

> Draft prerelease notes. Do not publish until the R3 cutover and release gates are complete.

ChatCockpit is a local-first **Development Continuity & Agent Routing Platform** for auditable handoff across ChatGPT Native, Direct Drive, Codex Session, and Async Agent Job workflows.

This alpha advances the product from the historical TokenPilot identity to the ChatCockpit canonical identity while preserving explicitly bounded compatibility inputs. It remains a development preview: it is not a hosted SaaS service, does not bypass platform limits, and does not claim Apple Developer ID or notarization certification.

## Identity Cutover

Fresh ChatCockpit operation now uses:

- package and CLI identity: `chatcockpit`;
- Source/Developer Mode local state root: `~/.chatcockpit/`; Packaged Mode continues to use `~/Library/Application Support/ChatCockpit/state/`;
- configuration environment prefix: `CHATCOCKPIT_*`;
- default repository id: `primary`;
- MCP namespace: `chatcockpit.*`;
- OAuth MCP scope: `chatcockpit:mcp`;
- built-in Direct Drive executor: `builtin-direct`;
- async runtime kind: `async-runner`;
- local resource source kind: `control-plane-local`;
- canonical OpenAPI source: `openapi/chatcockpit.openapi.yaml`.

Compatibility-period legacy inputs are intentionally receive-only where retained. They must not create new normal TokenPilot state or a second active product mode. On macOS, canonical ChatCockpit `start`/`restart` now quiesces and removes historical TokenPilot LaunchAgent plists before binding the control-plane port, preventing a legacy login-time service from becoming a second active runtime or causing a false-success mixed generation.

## Public API And MCP

- Canonical HTTP routes remain unbranded `/api/*` and `/mcp`.
- Canonical `/mcp` exposes a compact 24-tool ordinary-development core instead of flattening the entire configured catalog into the default model surface.
- Eight specialist surfaces remain explicit under `/mcp/packs/<pack>`; `/mcp/full` retains the complete 94-tool remotely routable compatibility catalog.
- `/tokenpilot/api/*` remains a bounded REST compatibility alias and `/tokenpilot/mcp` remains a receive-only alias of the full MCP compatibility surface during 0.2.x.
- `chatcockpit.tools.discover(pack, tool)` reports pack metadata plus one selected specialist tool's public schema/annotations without pretending MCP supports server-side dynamic catalog injection. Allowlisted Continuity/Runtime tools report `invokeVia=continuity.invoke`; allowlisted provider-native Codex tools report `invokeVia=codex.invoke`.
- `chatcockpit.continuity.invoke` is a bounded Core governance action with a stable forward-compatible `tool+input` envelope and a server-side fixed allowlist of 18 targets: all 16 `continuity-governance` operations plus Runtime restart/read. The selected target still validates its exact schema and original governance. Host administration, Device lifecycle, Workflow, Recovery, Resource mutation, and Codex Native operations cannot be dispatched through it.
- `chatcockpit.codex.invoke` remains a separate bounded Codex-domain Core gateway with the same stable `tool+input` envelope pattern and a server-side fixed allowlist of 11 provider-native targets for context/account/thread reads, Thread start/resume/fork, Turn start/interrupt, approval listing, and public-safe events. It does not expose approval decisions, legacy Codex Session compatibility actions, arbitrary provider methods, or non-Codex specialist tools.
- Provider-native `codex.thread.turn.start` now requires the explicit `modelLoopTransfer={kind:"operator-explicit", confirmation:"delegate-codex-model-loop"}` contract at both schema and service boundaries. This records an explicit delegation assertion but is not described as a local human-approval credential.
- All 24 default-core tools declare and server-validate `outputSchema`; output schema participates in MCP catalog fingerprinting.
- No `/chatcockpit/api/*` or `/chatcockpit/mcp` parallel route family is introduced.
- Every MCP surface emits only `chatcockpit.*` tools.
- Legacy `tokenpilot-direct` is accepted only as an input alias for the canonical `builtin-direct` executor.

## OAuth And Authentication

- Canonical MCP authorization uses `chatcockpit:mcp`.
- New local/OAuth opaque token families use `cc_*` prefixes.
- Historical grants do not silently gain the new scope; explicit reauthorization is required.
- Exposed-mode high-trust and Resource mutation guidance uses `CHATCOCKPIT_*` configuration names.

## Device Onboarding

- P10.1 adds Owner-only `GET /api/devices/onboarding` as the bounded server truth for device onboarding. The projection aggregates existing Trusted LAN, LAN discovery/TLS readiness, canonical Public Route, pending enrollment count, Hub public identity fingerprint, and currently valid CLI bootstrap capability without returning reusable credentials, private keys, or local paths.
- P10.2 adds the Web Cockpit **Add Device** wizard on top of that projection. Initial enrollment uses the canonical HTTPS Hub origin and the real installed-CLI `device connect` flow; the wizard never treats untrusted Bonjour/mDNS discovery as a first trust root.
- Nearby discovery is explicitly post-enrollment route optimization. The projection marks `nearby.initialEnrollment=false` and `remote.initialEnrollment=true`; after the target device has a Device ID and pinned Hub Ed25519 identity, `device discover --verify` may verify the matching Hub identity plus LAN TLS certificate proof before adopting pinned LAN TLS.
- Untrusted discovery (`device discover --json`) and post-enrollment LAN verification (`device discover --verify --json`) are separate commands. `npx` and native-package bootstrap remain explicitly unavailable while Phase 11 packaging is not shipped; the API and wizard do not advertise future distribution paths as runnable commands.

## Continuity And Runtime State

- Continuity schema advances through v19 for the ChatCockpit runtime identity cutover.
- Fresh runtime writes use `async-runner`, `control-plane-local`, and `primary`.
- Shared compatibility reads remain bounded for historical runtime values while target/canonical migration paths tighten new state to ChatCockpit identities.
- `.chatcockpit` and historical `.tokenpilot` runtime roots are both treated as private state by file, search, repository bundle, and public-safe Git boundaries.

## Runtime And Resource Center

- Runtime Profiles and append-only Resource Inventory remain public-safe projections over authoritative runtime/registry state.
- Governed Codex Skill enable/disable and Codex Plugin install/uninstall continue to use prepare/review/decision/execute semantics with authoritative refresh verification.
- Remote MCP cannot make the operator decision on its own.
- Exposed Resource mutation registration remains opt-in through `CHATCOCKPIT_RESOURCE_MUTATIONS_EXPOSED=true`.

## Direct Drive And Managed Processes

- Direct Drive preserves explicit model-loop ownership and the no-implicit-`turn/start` invariant.
- `workspace.exec` defaults to the native sandboxed managed-process lane. It also exposes an explicit `executionMode=host-managed` lane for the narrow allowlist of macOS build scripts that must create SwiftPM/Xcode child sandboxes; this lane reuses ChatCockpit's bounded built-in process supervisor, requires explicit `networkAccess=true`, and does not become an arbitrary shell escape hatch.
- Native managed processes now use multi-source terminal proof instead of trusting only the deferred Codex `command/exec` final response: a private stripped terminal sentinel or an explicit terminate request starts a cleanup fence against the exact App Server generation that started the process; writer authority is released only after that provider reports the process id absent/not running or the original final response arrives. A terminate acknowledgement or provider disconnect alone never becomes terminal truth, and abandoned final RPCs are removed with AbortSignal cleanup only after proof. A missing final response can therefore recover without a ghost writer authority while the same provider generation remains available; an unconfirmed/disconnected provider stays fail-closed for separate recovery.
- Host Root Alias, governed file mutation, bounded Host Command, and Managed Workspace Process flows remain approval- and evidence-governed.
- The Process Supervisor sidecar continues to own private downstream PID/runtime state while public APIs use ChatCockpit-owned process identities.

## Integrations, OpenAPI, And Web UI

- `openapi/chatcockpit.openapi.yaml` is the single canonical OpenAPI truth source.
- `/ui/integrations` is the primary integration surface: ChatGPT App / MCP first, API & OpenAPI advanced, Custom GPT Actions compatibility-only.
- Legacy `/ui/gpt-helper` remains receive-only during 0.2.x and redirects to `/ui/integrations`.
- Operator Console, Continuity Workbench, Resource Center, and Integrations visible copy use ChatCockpit and current `CHATCOCKPIT_*` guidance.
- Fresh-install documentation uses global `~/.chatcockpit`, `chatcockpit` CLI commands, and `chatcockpit.*` MCP tools.

## Compatibility Boundary

The 0.2.x compatibility period may still recognize selected historical inputs such as:

- `/tokenpilot/api/*` and `/tokenpilot/mcp` receive-only HTTP aliases;
- historical `.tokenpilot` runtime state for migration/read safety;
- legacy identity values required to migrate or inspect existing state.

R4 completed the public GitHub repository rename, so current first-party repository links now use the ChatCockpit repository identity. These compatibility surfaces do not authorize fresh normal writes under the old identity.

## Security And Privacy

Before a prerelease is published, the release commit must pass the repository verification, public/private knowledge boundary, current-tree privacy checks, and the full Git-history privacy scan. No release should treat an incomplete or timed-out history scan as a pass.

Real deployment domains, bearer tokens, tunnel credentials, private IPs, local absolute paths, and machine-specific runtime state must remain outside public Git history.
